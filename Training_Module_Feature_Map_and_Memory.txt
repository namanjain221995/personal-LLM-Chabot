A1. EXECUTIVE SUMMARY -- WHAT THE TRAINING MODULE IS
--------------------------------------------------------------------------------

Techsara runs technical training programs and places the graduates at client
companies. The "training module" is everything in Salesforce that makes one
candidate's training run end to end, plus the Experience Cloud portal the
candidate logs into to live it.

Read as a story, it is this:

  1. An admin AUTHORS a program.
     Program__c -> Program_Version__c -> a list of StepTemplate__c rows.
     The Program_Version carries every behavioural switch: how long sessions are,
     who books them, whether there are mock interviews, how often, what happens
     if a mock is missed. Authoring happens in one screen flow: Program_Creation.

  2. An admin SCHEDULES a cohort.
     Cohort__c (called a "Slot" in the UI) gets one or more Session_Window__c
     rows -- reusable daily time windows like "Batch 1: Mon-Fri 7-9 PM ET" --
     each with a trainer, a capacity and a time zone.

  3. A candidate is ENROLLED.
     Candidate_Training__c is the per-candidate instance of a Program_Version.
     Creating it fans out CandidateTrainingStep__c rows (one per StepTemplate)
     and Deliverable__c rows (the assignments).

  4. The candidate LOGS IN to the portal.
     Not as a Salesforce user -- as the site's Guest User, holding a custom
     session token. Seven tabs: Overview, Deliverables, Training, Sessions,
     Mock Interview, Academic Planner, Today's To-Do.

  5. The candidate BOOKS their slot.
     Self-service session-window picker. Booking assigns the cohort, converts
     every time into the candidate's zone, computes each step's start date with
     working-day math, and back-fills every deliverable's due date.

  6. Live SESSIONS happen.
     Session__c per meeting, Session_Attendee__c for everyone else in a group
     session. Zoom links are created by a callout flow; calendar events sync.
     Completing a session activates the deliverables attached to that step.

  7. The candidate SUBMITS deliverables.
     Pre-signed S3 upload (or Monaco code editor), then an AWS Lambda grades it
     with AI and POSTs the score back to a Salesforce REST endpoint.

  8. MOCK INTERVIEWS gate progress.
     Per-program cadence (Weekly / Once / End of Program / Custom-after-step).
     The candidate self-books a slot from a live availability engine built out
     of Business Hours minus each interviewer's Salesforce calendar. A trainer
     records Pass/Fail within N working days or the training auto-drops.

  9. Admins WATCH the whole cohort.
     Admin Training Dashboard -- list view per slot, chart view org-wide, every
     legend and bar clickable into a drill drawer.

 10. Anything that goes wrong CASCADES cleanly.
     One field flip (Candidate_Training.Status__c = 'Dropped') tears down
     deliverables, steps, sessions and attendee rows through a single flow.

Everything in PART C is one of those ten beats, expanded.

A2. THE LICENSING CONSTRAINT AND THE ARCHITECTURAL ANSWER
--------------------------------------------------------------------------------

THE CONSTRAINT
  Salesforce charges roughly USD 5-15 per active user per month. Techsara's
  projected scale is 500-2000 concurrent candidates. Licensing each candidate
  would cost USD 30K-240K per year for what is, functionally, a read-mostly
  student portal.

  So: the portal must work with ZERO Salesforce licenses per candidate.

THE ANSWER
  The portal is an LWR Experience Cloud site. Every visitor -- including a fully
  logged-in candidate -- is the site's Guest User as far as the Salesforce
  platform is concerned. There is no per-candidate User record.

  Identity is layered on top in application code:

    Candidate_Portal_Credential__c   the "user account"   (username/password)
    Candidate_Portal_Session__c      the "session cookie" (random token, 7d TTL)

  The LWC holds the token in localStorage and passes it into every Apex call.
  Apex resolves it to a candidate Id, then filters every query by that Id.

WHAT THAT BUYS AND WHAT IT COSTS
  Buys : zero license cost, full control of the login UX, one credential model
         shared by the LWR portal AND the separate Next.js front end.
  Costs: Salesforce's own record-level security is doing NOTHING for you. The
         Guest User either sees everything the perm set grants or nothing. All
         isolation is enforced by discipline in Apex. Hence A3.

A3. THE ONE NON-NEGOTIABLE PATTERN
--------------------------------------------------------------------------------

Every @AuraEnabled method that touches candidate data starts with one line:

    CandidateContext ctx = CandidateContext.fromSession(sessionId);

and every SOQL query in that method filters by ctx.candidateId.

    // WRONG -- this is a vulnerability, not a style issue.
    // A candidate can paste another candidate's record Id.
    SELECT Id, Status__c FROM Deliverable__c WHERE Id = :requestedId

    // RIGHT
    SELECT Id, Status__c FROM Deliverable__c
    WHERE Id = :requestedId
      AND Candidate_Training__r.Candidate__c = :ctx.candidateId

Three refinements the codebase has learned since that rule was first written:

  (a) CACHEABLE READS MUST USE fromSessionReadOnly, NOT fromSession.
      fromSession() writes the session heartbeat. That is a DML. An
      @AuraEnabled(cacheable=true) method runs in a read-only context and
      throws "Too many DML statements: 1" the moment it tries. The failure is
      invisible in local tests, in System.runAs, and to an admin -- it only
      appears at the Guest User's Lightning cacheable boundary. Symptom: the
      page renders blank while the records plainly exist.
      See PART N, gotcha N-12.

  (b) BEFORE AN HTTP CALLOUT, ALSO USE fromSessionReadOnly.
      Apex forbids DML before a callout in the same transaction. After the
      callout returns, call CandidateContext.touchHeartbeat(ctx.sessionRecordId)
      to record activity.

  (c) FROM A REST CONTEXT, USE fromSessionRest.
      fromSession throws AuraHandledException, which is ILLEGAL to throw from a
      @RestResource. It becomes an uncatchable System.LimitException and takes
      the whole REST request down. fromSessionRest throws a catchable
      CandidateContext.SessionException instead. Same split exists on the login
      path: AuthService.loginInternal (catchable) vs AuthService.login
      (Aura-facing). See PART N, gotcha N-20.

A fourth rule, learned the hard way, is about what you return rather than what
you query -- see B3.

B2. REQUEST LIFECYCLE END TO END
--------------------------------------------------------------------------------

LOGIN

   1. Candidate opens https://<host>/<siteslug>/login
      Note: LWR has NO /s/ prefix. The LWC computes the site prefix from
      window.location.pathname at runtime rather than hard-coding it.

   2. candidateLogin calls AuthService.login(username, password, clientIp).

   3. AuthService (without sharing):
        - both fields required, else the generic error
        - SOQL the credential by Username__c
        - guards: no match / Is_Active__c = false / Locked_Until__c > now
        - constant-time password compare (no timing side-channel)
        - on mismatch: Failed_Login_Count__c++, and at 5 set
          Locked_Until__c = now + 15 minutes
        - enforce the device cap; deactivate the oldest session if over
        - insert Candidate_Portal_Session__c with a random 32+ char token,
          Expires_At__c = now + session hours
        - reset the failure counters, stamp Last_Login_At__c
        - return the token string

      Every failure mode returns the SAME message, "Invalid username or
      password". No username-existence disclosure.

   4. The LWC writes the token to localStorage via c/sessionUtil.setSession()
      and sets sessionStorage 'justLoggedIn' = '1' for the welcome animation.

   5. Redirect to the portal home.

AUTHENTICATED CALL

   6. candidateHome mounts, reads the token, renders the tab shell, and each
      tab component calls its Apex method with the token.

   7. Apex: CandidateContext.fromSession(token) (or fromSessionReadOnly for
      cacheable reads) validates:
        - token found
        - Is_Active__c = true
        - Expires_At__c > now
        - parent credential still active
      then resolves candidateId from the credential, updates
      Last_Activity_At__c (sliding heartbeat), and returns the context.

   8. The service builds its DTO with every query filtered by ctx.candidateId,
      and formats every date, time and status string IN APEX.

   9. The LWC renders pre-formatted strings. It does no locale work.

WRITE ACTION (example: submitting a deliverable)

  10. deliverables -> deliverableCard -> s3Upload
  11. createPendingResult -> a Deliverable_Result__c row in Pending
  12. getUploadUrl -> AWSTrainingIntegration asks AWS for a pre-signed PUT
      (fromSessionReadOnly here -- callout, so no DML first)
  13. The browser PUTs the file straight to S3. It never passes through
      Salesforce, so the 6 MB heap and 12 MB request limits never apply.
  14. finalizeSubmission -> Deliverable__c.Status__c = Submitted
  15. AWS grades asynchronously and POSTs to DeliverableResultRest
  16. Deliverable_result_roll_up_status flow rolls the result up to the parent
  17. Next portal load shows the score and feedback

LOGOUT
  AuthService.logout(token) sets Is_Active__c = false. The row stays for audit;
  every later fromSession on that token throws.

B3. THE DTO BOUNDARY RULE (AND WHY RAW sOBJECTS ARE FORBIDDEN)
--------------------------------------------------------------------------------

RULE: a portal Apex method NEVER returns a raw sObject or a List<sObject> to
the LWC. It returns a DTO -- a plain class with @AuraEnabled fields.

The original reason was formatting discipline: all locale, date and status
formatting happens in Apex so the LWC stays dumb and the same DTO can feed a
second front end (the Next.js portal) without duplicating logic.

The second reason was discovered painfully. [MEMORY, availability portal build]

  AvailabilityPortalController.getMyAvailability first returned
  List<Availability__c>. As an admin it worked. In the portal the grid was
  EMPTY -- and creating a slot appeared to do nothing.

  Cause: at the Guest User's Lightning boundary, Salesforce STRIPS fields the
  running user has no FLS on. The rows arrived with null times, and the LWC's
  own filter dropped every one of them. The records had been saved correctly
  the whole time.

  System.runAs(guestUser) does NOT reproduce this, because Apex-to-Apex runs in
  system mode. Only a real request through the Lightning boundary shows it.

  Fix: return a SlotDTO (plain @AuraEnabled class -- no FLS applies), and make
  update/delete return void.

So the rule has teeth: DTOs are not a style preference, they are what makes the
Guest User architecture work at all.

--------------------------------------------------------------------------------
B4. TIME ZONE STRATEGY
--------------------------------------------------------------------------------

Time zones are the single most bug-prone part of this codebase. Four different
representations coexist, on purpose.

  1. TRUE UTC DATETIMES
     Session__c.Scheduled_Start__c / Scheduled_End__c,
     Availability__c.Start_DateTime__c / End_DateTime__c.
     These are the only trustworthy values for arithmetic. Legacy Session rows
     often have them null -- see rule 4.

  2. PRE-FORMATTED DISPLAY STRINGS
     Session__c.Selected_Time_Zone_Start_Time__c, Selected_Time_Zone_ETim__c,
     Start_Time_IST__c, End_Time_IST__c;
     Candidate_Training__c.Candidate_Time_Zone_Start_Time__c / _End_Time__c,
     Start_Tme_IST__c (note the typo in the API name), End_Time_IST__c.
     These exist so a record page and an email can show a time without any
     conversion logic. They are STRINGS. Never parse them for math unless you
     are reconstructing a missing UTC value.

  3. EASTERN-NORMALISED MIRRORS
     Availability__c.Date_EST__c, Start_Time_EST__c, End_Time_EST__c, written by
     AvailabilityTriggerHandler.applyEasternFields on every insert/update.
     Eastern is the org's canonical comparison zone, so overlap and clash
     detection can compare apples to apples.

  4. RECONSTRUCTION FOR LEGACY ROWS
     PortalHelpers.sessionUtcFromLocal(localDate, localTimeStr, sourceTzLabel)
     rebuilds a UTC Datetime out of Scheduled_Date__c plus the display strings
     plus Time_Zone__c, for the rows that predate Scheduled_Start__c.

CONVERSION HELPERS
  PortalHelpers.tzIdFromLabel(label)  picklist label -> IANA id
  EasternTimeUtil                     ZONE_TO_IANA map, toEastern / fromEastern,
                                      rangeToEastern / rangeFromEastern,
                                      isKnownZone, isEastern, toMinutes,
                                      parseIsoDate, nextDay, prevDay

PER-VIEWER CONVERSION FOR GROUP SESSIONS
  One Session__c can be attended by candidates in different zones. Showing the
  master record's stored strings to everybody was wrong. DashboardService
  .mapSessions now converts per viewer, using the viewer's own
  Candidate_Training__c.Time_Zone__c. Shipped to all four orgs 2026-07-20.

THE IST TRAP [MEMORY, 2026-08-11]
  The Candidate_Time_Zone global value set has 8 values: ET (default), PT, CT,
  MT, HT, UTC, AT and IST (India Standard Time). IST was MISSING from both the
  LWC's ZONE_IANA map and EasternTimeUtil.ZONE_TO_IANA, so anything set to IST
  silently fell back to Eastern -- a 9.5 hour error that never threw. Fixed by
  adding 'IST (India Standard Time)' => 'Asia/Kolkata' to both maps.

  Corollary: when you add a picklist value to a zone field, grep for BOTH maps.
  A missing entry degrades silently instead of failing loudly.


--------------------------------------------------------------------------------
B5. TWO RUNTIME PERSONAS
--------------------------------------------------------------------------------

The same objects are reached by two completely different security models. Know
which one you are writing for before you pick a sharing keyword.

  PERSONA 1 -- THE CANDIDATE (Guest User, portal)

    Runs as        : the Experience site's Guest User
    Sharing        : classes are `without sharing` on purpose
    Record access  : ZERO from the platform. Enforced entirely by
                     CandidateContext + ctx.candidateId filters
    Object access  : granted by Candidate_Portal_Guest_Access perm set,
                     assigned to the SITE'S Guest User

    Classes        : AuthService, CandidatePortalController,

    Edit or Delete object permissions. Deploying a perm set with allowEdit or
    allowDelete for the Guest fails with "The user license doesn't allow the
    permission". Availability__c is therefore granted Read + Create only --
    and edit/delete still work, because `without sharing` system-mode Apex

    assertOwned() IDOR check.

  PERSONA 2 -- THE INTERNAL USER (recruiter, trainer, admin)

    Runs as        : a real licensed Salesforce user
    Sharing        : `with sharing` where the platform's rules should apply
    Record access  : normal Salesforce sharing
    Object access  : Training_Module_All_Access, Admin_Training_Dashboard_Access,

    Returns        : DTOs for the dashboards, sObjects are acceptable elsewhere
    Classes        : AdminDashboardController, AvailabilityController,

    Where both personas need the same feature, the codebase builds a TWIN, not

    AvailabilityPortalController (portal, without sharing) are the canonical

    toInterviewInfo, toSessionInfo, buildRow, useViewZone, applyViewZone -- so
    there is exactly one time-conversion implementation.

    CRITICAL [MEMORY 2026-08-11]: those five helpers must stay `public`. A
    refactor changed them to private/@TestVisible, which compiled fine for the
    internal class and produced NINE "Method is not visible" errors in the
    portal twin, taking the portal calendar down in dev9. They are public by
    design. Leave them public.

    The same twin idea shows up as MockAvailabilityService (portal booking)
    vs Interview_Create_Reschedule_Flow (trainer booking) -- one storage model,

AUTOMATION
  None. Auth is pure Apex, deliberately -- no flow can silently change it.

CONFIG
  Apex constants in AuthService:
    LOCKOUT_THRESHOLD       = 5
    LOCKOUT_MINUTES         = 15
    FALLBACK_SESSION_HOURS  = 168 (7 days, used when the CMDT is missing)
    FALLBACK_MAX_DEVICES    = 2
    GENERIC_LOGIN_ERROR     = 'Invalid username or password'
  Live values come from Candidate_Portal_Setting__mdt.Default and override the
  fallbacks. Note the CMDT cannot be changed by DML -- edit the customMetadata
  record in the repo and deploy it, or use the Setup UI.

RULES
  - One message for every failure. Wrong username, wrong password, deactivated
    account and locked account all return the identical string.
  - Constant-time compare so response latency cannot leak the prefix match.
  - Device cap evicts the OLDEST active session rather than refusing the login.
  - Logout does not delete the session row; it deactivates it, keeping the audit
    trail intact.
  - recoverLogin emails the username and the plaintext password to the ACCOUNT
    OWNER (the recruiter/POC), not to the candidate. Credentials stay inside
    staff mailboxes and the POC forwards them. It DOES reveal whether an email
    is registered -- an accepted product tradeoff.
  - Username convention is mandatory: firstname.lastname@talenthub.com, all
    lowercase, fake domain. Never the candidate's real email. Set
    Is_Active__c = true and Failed_Login_Count__c = 0 on creation. Password
    format in use: Firstname@ + 4 random digits, e.g. Usha@1332.

GOTCHAS
  - AuraHandledException cannot be thrown from a REST context. That is why
    loginInternal and fromSessionRest exist. Unit tests do NOT catch this --
    the test context is exempt, so only a live REST call reproduces it.
  - Clearing stuck sessions during testing:
      UPDATE Candidate_Portal_Session__c SET Is_Active__c = false
      WHERE Is_Active__c = true
    (anonymous Apex).
  - The Guest User must have Candidate_Portal_Guest_Access assigned, and it must
    be the guest user OF THE SITE THE CANDIDATE IS ACTUALLY HITTING. This has
    been mis-assigned in production before -- see feature 02 and gotcha N-01.

STATUS
  Live on all four orgs. Role__c and the REST split are dev9-only pending
  approval [MEMORY 2026-08-03] -- and they MUST ship together with
  StemPortalAuthRest, or REST login crashes on every failure path.

FEATURE 06 -- SESSION WINDOW BOOKING (SELF-SERVICE SLOT PICKER)
================================================================================

WHAT
  A candidate whose program is configured for "Candidate Books" picks their
  daily time window themselves. Booking is not just an assignment -- it is the
  single transaction that materialises the candidate's whole schedule: cohort
  assignment, time-zone conversion, per-step start dates and every deliverable
  due date.

WHO
  Candidates on Candidate-Books programs. Admins have an override (feature 17).

ENTRY POINT
  Portal -> Training tab -> the tile shows the picker when needsBooking is true.

UI
  trainingSlotPicker (12 KB)
    - shows the available windows as selectable cards
    - uses the browser time zone for first paint, then Apex overrides with the
      candidate's own profile zone from their training's Time_Zone__c
    - full-panel spinner overlay during the async call, armed with a DOUBLE
      requestAnimationFrame so the spinner is guaranteed painted before the
      Apex call starts

APEX
  CandidatePortalController
    getBookableSessionWindows(sessionId, trainingId, candidateTzId)
        -> List<PortalDtos.SessionWindowSlotDTO>
        filters Status__c = 'Upcoming'
            AND (Activate_From__c <= TODAY OR Activate_From__c = null)
    bookSessionWindow(sessionId, trainingId, sessionWindowId)

OBJECTS
  Session_Window__c [VERIFIED fields]
    Cohort__c, Program_Version__c (REQUIRED), Trainer__c (Recruiter),
    Window_Label__c, Sequence__c,
    Start_Time__c, End_Time__c, Time_Zone__c,
    Start_Date__c, Activate_From__c,
    Status__c (Upcoming / Active / Completed), Candidate_Capacity__c,
    Booked_Count__c
    Autonumber name: SW-{0000}

  Written on booking: Candidate_Training__c (cohort, window, dates, zone strings,
  assigned trainer), CandidateTrainingStep__c (Started_At__c per step),
  Deliverable__c (three due-date fields), Session__c or Session_Attendee__c.

RULES -- what bookSessionWindow actually does, in order
   1. Validate the session and resolve the candidate.
   2. SELECT ... FOR UPDATE on the Session_Window row. This row lock is the
      race guard against two candidates taking the last capacity slot at once.
   3. Assign Cohort__c and Session_Window__c onto the Candidate_Training.
   4. Convert the window's start/end times from the window's zone into the
      candidate's zone; write the display strings.
   5. Copy Session_Window.Trainer__c onto Candidate_Training.Assigned_Trainer__c
      so the trainer is visible on the training record. (Added mid-2026;
      29 production trainings had to be back-filled because they predated it.)
   6. Compute each step's Started_At with working-day math:
        validStartDate(d)   Saturday or Sunday bumps forward to Monday
        nextBusinessDay(d)  Friday +3, Saturday +2, Sunday +1, otherwise +1
      These deliberately mirror the flow formulas fx_ValidStartDate and
      fx_NextBusinessDay so Apex and flow never disagree.
   7. Set Candidate_Training.End_Date__c.
   8. Create the Session records -- but only for the FIRST candidate into a
      group window. Every subsequent candidate gets a Session_Attendee__c row
      pointing at the existing sessions (feature 07).
   9. Recompute every deliverable's due date:
        due = step.Started_At.date() + Deliverable.Days_To_Complete__c
        Due_Date_IST__c                    = "M/D/YYYY {training.End_Time_IST__c}"
        Due_Date_Candidate_Time_Zone__c    = "M/D/YYYY {training.Candidate_Time_Zone_End_Time__c}"
        Due_Date_Sort__c                   = that date at 18:30

GOTCHAS
  - Session_Window.Program_Version__c is REQUIRED. A permission set therefore
    cannot carry an explicit <fieldPermissions> entry for it -- required fields
    get implicit access through objectPermissions, and an explicit entry fails
    the deploy.
  - Cohort to Session_Window was originally 1:1, enforced by the
    Session_Window_Enforce_Unique_Cohort before-save flow. The architecture
    later moved to 1:many (multi-window cohorts). Check which behaviour a given
    org has before assuming.

RULES -- CADENCE
  Weekly     [MEMORY v6.3] EVERY mock, regular and final alike, lands on
             Mock_Cadence_Day of the NEXT calendar week, spaced 7 days apart.
             [MEMORY v6.4] If Mock_Final_Week_Day is set, the final mock is
             overridden to the first occurrence of that weekday on or after the
             training end date.
  Once       v1 treats this the same as End of Program.
  End of Program  a single mock on the last working day.
  Custom     one mock per StepTemplate with Triggers_Mock__c = true, landing on
             the next working day after that step's Started_At.

RULES -- AVAILABILITY ENGINE
   1. Read the Public Group named in pv.Mock_Interviewer_Group__c.
   2. GroupMember -> User Ids.
   3. Map User Ids to Recruiter__c through Recruiter__c.Recruiter_User__c.
   4. Load the org's Default Business Hours for that weekday -> time bounds.
   5. For each interviewer, load their Salesforce Events overlapping the date,
      plus their existing mock bookings.
   6. Free window = Business Hours MINUS events MINUS bookings.
   7. Also subtract the CANDIDATE's own busy ranges (loadCandidateBusyRanges),
      so a candidate cannot book a mock over their own training session.
   8. Slice into blocks of Mock_Duration_Min stepping by
      Mock_Slot_Granularity_Min.
   9. Return per-slot { start, end, availableCount }.
  10. If the day yields fewer than Mock_Overflow_Threshold free slots, open the
      NEXT bookable day too, and keep going up to MAX_OVERFLOW_DAYS = 10. Each
      slot is stamped with its own date so the picker can show multiple days.
      Holidays are excluded via loadHolidayDates.

RULES -- SLOT ALIGNMENT AND INTERVIEWER CHOICE
  [MEMORY v6.5] The first slot anchors to the BUSINESS HOURS START, not to a
  granularity boundary measured from midnight. With 09:30 BH start and 60-minute
  granularity, the old behaviour silently threw away the 09:30-10:30 slot.
  [MEMORY v6.8] pickFreeInterviewer is LEAST-LOADED, not random: filter to those
  free at that slot, take the lowest count of open mocks, break ties randomly.

GOTCHAS
  - [MEMORY v6.6/v6.7] Candidate_Training.Niche__c is a PICKLIST but
    Internal_Interview.Niche__c is a LOOKUP to the Niche__c object. Copying one
    into the other throws. lookupNicheId(String) resolves the picklist label to
    the lookup Id by name -- which means the names must match exactly. A
    production niche had to be renamed from "AIML Engineer" to "AI ML Engineer"
    for the lookup to succeed.
  - Lazy creation: the Internal_Interview row is created ONLY when the candidate
    books. Expected-but-unbooked mocks exist purely as calculator output.
  - [MEMORY v6.1] New bookings default to Status__c = 'Unscheduled', which is
    what triggers the Zoom callout flow.
  - The interviewer's NAME is deliberately never shown to the candidate.

STATUS
  LIVE ON ALL FOUR ORGS INCLUDING PRODUCTION since 2026-07-27, iterated through
  v6.9+. The older knowledgebase's "TODO / in progress" markings are obsolete.

FEATURE 26 -- NEXT.JS "STEM PORTAL" REST FACADE
================================================================================

WHAT
  A second candidate front end, built in Next.js in a separate repository, that
  logs in with the SAME credentials as the LWR portal. Salesforce becomes a
  headless backend reached over REST. One lockout policy, one device cap, one
  token model, zero duplicated auth logic.

ARCHITECTURE (chosen as "Route A")
  Next.js server
    -> OAuth Client Credentials (an integration user as Run-As)
    -> thin Apex REST facade
    -> reuses AuthService + CandidateContext

  Chosen over a public-guest-Site approach because Next.js has a server tier
  that can hold the secret, and the org already runs this exact pattern for AWS
  (DeliverableResultRest).

APEX
  StemPortalAuthRest (180 lines, @RestResource)
    @HttpPost handlePost()   routes /login and /logout
    @HttpGet  handleGet()    /me
    URL: /services/apexrest/v1/portal-auth/*
      POST /login  {username, password, clientIp} -> {ok, token, candidate, role}
      POST /logout {token}                        -> {ok}
      GET  /me     header Candidate-Session       -> {ok, candidate}

  StemPortalDataRest (129 lines, @RestResource)
    @HttpGet handleGet()
    URL: /services/apexrest/v1/portal-data/*
      GET /niches     -> {ok, count, niches:[{id, name, domainType, isActive}]}
      GET /candidates -> {ok, count, candidates:[{candidateId, name, email,
                          phone, username, role, isActive, lastLoginAt}]}

  Tests: StemPortalAuthRestTest, StemPortalDataRestTest

THE CONTRACT QUIRK THAT MATTERS
  Bad credentials, a lockout, or an expired session return HTTP 200 with
  ok:false -- NOT 401. Only 400/404/500 come out of Apex; a 401 can only come
  from the Salesforce OAuth layer.

  Why: the Next.js client retries once on 401. If a failed login returned 401,
  the retry would re-POST the login and DOUBLE-INCREMENT the lockout counter.
  Splitting the two makes "your password is wrong" a normal outcome and "your
  app token expired" the only retryable one.

ROLE-BASED LOGIN
  Candidate_Portal_Credential__c.Role__c -- restricted picklist, Candidate
  (default) / Manager. The login response carries a top-level lower-cased role
  ('manager' | 'candidate'), resolved by an isolated roleFor(username) query and
  falling back to 'candidate' when blank or unknown.

  THE CLIENT MUST NEVER ASSERT ITS OWN ROLE. Salesforce decides.

  Flip a role from the CLI:
    sf data update record -o dev9 --sobject Candidate_Portal_Credential__c
       --where "Username__c='...'" --values "Role__c=Manager"

WHY THE DATA ENDPOINTS ARE NAMED ROUTES
  A generic "query any object" endpoint was proposed and REJECTED: it would
  expose Password__c, the User object and all candidate PII. Every new
  reference list gets its own small named route instead. /candidates returns
  all-candidate PII and MUST be gated to managers by the backend.

SECURITY CONFIG
  External Client App "Nextjs Portal Backend", Client Credentials flow.
  Permission set Stem_Portal grants the Apex class access.
  Permission set Stem_Portal_Field_Admin grants admin FLS on Role__c (needed for
  CLI/UI edits; NOT needed by the endpoint, since Apex runs in system mode).

  THE BLOCKER EVERYONE HITS: granting the class in the perm set is only half the
  job. The perm set must also be ASSIGNED TO THE RUN-AS USER. A non-admin
  integration user without it gets HTTP 403 "no access to Apex class". And
  "invalid_grant: no client credentials user enabled" means the Run-As user was
  never set in the ECA policies.

  The consumer secret was pasted in plaintext during setup. ROTATE IT BEFORE
  PRODUCTION.

NEXT.JS SIDE
  .env.local: SF_INSTANCE_URL, SF_TOKEN_URL, SF_CLIENT_ID, SF_CLIENT_SECRET.
  Store the portal token in an httpOnly cookie. Cache the app token server-side
  and retry once on 401. No CORS needed -- it is server to server.

STATUS
  Salesforce side COMPLETE AND VERIFIED on dev9 (2026-08-01), full chain proven
  end to end. Role-based login is dev9-only pending approval. The Next.js side
  is the remaining work. Rollout rule: AuthService and CandidateContext changes
  MUST ship together with StemPortalAuthRest and Role__c, or REST login crashes
  on every failure path.

WHAT
  The trainer-scoped sibling of the Admin Training Dashboard (feature 18). A
  trainer picks a slot, sees ONLY the trainings they are the assigned trainer
  on, clicks one, and gets that training's DELIVERABLES ONLY -- no modules, no
  sessions, no mocks.

  cohort with four drill tabs. This shows a trainer their own handful of
  candidates and one drill. A trainer opening feature 18 would see 582 trainings
  and have to hunt for their 35.

  every training in the slot and defeat the entire feature. One constant flips

      503 trainings reach their trainer via Assigned_Trainer__c -> Recruiter
        2 trainings reach their trainer via Assigned_Trainer_User__c
  Matching only the obvious "assigned trainer" User lookup would have produced an
  empty dashboard for essentially everyone.

SECURITY MODEL
  Mirrors the portal's CandidateContext pattern, adapted to real users.

  1. Identity is derived server-side from UserInfo.getUserId(). It is NEVER a
     method parameter. There is no client-supplied scope input at all -- the
     original allTrainers flag was REMOVED on 2026-08-13 precisely to close
     that surface.
  2. getMyTrainingDeliverables() calls assertAccessible() BEFORE reading
     anything. Filtering the LIST is not sufficient -- the drill method is
     callable with any Id. Same IDOR guard as
     AvailabilityPortalController.assertOwned.
  3. `without sharing` is deliberate. Trainers frequently lack record-level
     sharing on the candidate Accounts they train, so platform sharing would
     hand them an empty dashboard. The trainer filter is what enforces
     isolation, exactly as ctx.candidateId does in the portal.
  4. Every return is a DTO, never an sObject -- so no FLS stripping at the
     Lightning boundary, and therefore NO object or field permissions are
     required. See PART B3.

  isPrivileged() passes on EITHER route:
    a. the Trainer_Dashboard_View_All CUSTOM PERMISSION (the one to hand out --
       scoped to this dashboard, grants no record access anywhere else), or
    b. View All Data via profile or perm set (so System Admins just work).
    Checked via FeatureManagement.checkPermission wrapped in try/catch, then
    PermissionSetAssignment (which covers profiles, since a profile is itself an
    IsOwnedByProfile permission set).
    NEVER key this off a profile NAME. Profiles get cloned and renamed.

DELIVERABLE BUCKETS -- exhaustive by design
    approved + submitted + overdue + pending + dropped == totalCount

  Overdue = past Due_Date_Sort__c AND the CANDIDATE still owes it. It EXCLUDES:
    - Submitted : that is the TRAINER's review queue, not the candidate's debt.
                  Flagging it red would double-count it and blame the wrong
                  person.
    - Dropped   : the training is gone; chasing it is noise.
    - Approved  : obviously.

  This DIFFERS from the admin dashboard's list-view overdue
  (dueByToday - approved), which does count submitted as overdue. The two are
  answering different questions and the divergence is intentional.

  THE BUG THIS FIXES: a real screenshot showed a dropped training reading
  36 total / 15 approved / 0 awaiting / 0 overdue -- with 21 dropped rows
  silently unaccounted for. droppedCount exists so the tiles always sum.

  progressPct ignores dropped rows: approved / (total - dropped). Counting them
  in the denominator permanently caps a dropped candidate's bar at an arbitrary
  number and reads as a data error.

  The LWC's bucketOf() MUST mirror the Apex rollup exactly, or a tile says 6 and
  the filtered table shows 5. No test covers that pairing -- it spans Apex and
  JS. If you change bucket rules, change both.

DRAWER INTERACTION
  - Stat tiles double as FILTERS (delFilter). Clicking "Overdue" filters the
    table to overdue rows and shows a clear-filter bar. A trainer with 36
    deliverables jumps to the 3 that need action instead of scanning.
  - The Dropped tile renders ONLY when droppedCount > 0.
  - Clicking a deliverable ROW opens the Deliverable record via NavigationMixin
    (standard__recordPage). Works in internal Salesforce and Experience Cloud.

    ACCESS CONSEQUENCE, IMPORTANT: everything else here reads through
    system-mode Apex returning DTOs and needs NO object permissions. This one
    link hands the user to the PLATFORM's record page, which enforces object
    read + FLS + record sharing normally. A community trainer without
    Deliverable__c access lands on "insufficient privileges". Granting it is a
    real widening of access. The alternative -- an in-drawer detail panel fed by
    Apex -- was discussed but NOT built.

STYLING
  Tokens and typography are copied from adminTrainingDashboard.css so the two
  dashboards read as one system. The rule that was initially got wrong:

    Georgia serif  -> HEADINGS ONLY (page h1, group headers 15px, drawer h2 20px)
    sans-serif 700 -> ALL NUMBERS, with font-variant-numeric: tabular-nums,
                      letter-spacing -0.01em, word-spacing -1px

  Tile values were briefly Georgia serif, which is what made the two dashboards
  look different. Tabular numerals matter -- they stop counts jittering between
  rows. Tiles also carry a 3px left accent stripe, 6px radius, 12x14 padding,
  matching feature 18 exactly.

  CSS lives in the component's own file per project convention; the static
  resource is for cross-component tokens only. Filter/toolbar containers use
  overflow: visible -- see PART N on clipped dropdown popovers.

DESIGN DECISIONS
  1. New component, not a toggle on the admin dashboard. The admin dashboard is
     live on 4 orgs for a different audience; a hard "only mine" filter would
     have broken it.
  2. Reuse the admin aggregation, restrict the result, recompute the summary.
  3. Exclude Cohort lead trainer from the access filter (keep it for display).
  4. Deliverables ONLY in the drill -- explicitly what was asked for.
  5. One table shape, not feature 18's two-table IRT split. Not needed here and
     the split exists only because of a template-parser limitation (PART N).
  6. No UI scope toggle. Scope is a permission, not a control.
  7. Custom permission instead of View All Data, so oversight does not require
     org-wide record access.
  8. Buckets exhaustive and mutually exclusive.
  9. Tests borrow an existing non-privileged user rather than inserting one.

TESTING NOTES -- why the tests look unusual
  The scoping tests run as a REAL, EXISTING non-privileged user found at
  runtime, via System.runAs. Running as the default admin would prove nothing:
  View All Data short-circuits every guard.

  They do NOT insert a User, because that is setup-object DML (mixed-DML
  gymnastics) AND consumes a licence, which can fail a PRODUCTION deploy with
  LICENSE_LIMIT_EXCEEDED. [VERIFIED] every org has spare non-admin standard
  users: dev9 9, dev10 16, preprod 21, prod 24.

  User, Profile and PermissionSetAssignment are setup objects and ARE visible in
  tests without SeeAllData. Candidate_Training__c and Recruiter__c are not, so
  the counts only ever see test-created data.

  Every scoping test guards on the borrowed user being found;
  privilegedUserSeesEverythingAndBypassesTheGuard always runs so coverage
  survives on an org with no borrowable user.

  The custom-permission test assigns the perm set inside
  System.runAs(currentUser) to dodge MIXED_DML_OPERATION.

  D5.12  TRAPS
  ------------
  T1  The object's View action override points at FlexiPage
      Candidate_Training_Record_Page, which IS NOT IN THIS REPO. A full-org
      deploy of this object from this repo references a page it does not ship.

  T2  Cohort__c the OBJECT is not source-controlled (see D3). Its shape cannot
      be verified here. AdminDashboardController deliberately uses
      Database.query() for EVERY Cohort__c access -- the usual tell that an
      object is not guaranteed to exist at compile time. Copy that habit.

  T3  Start_Tme_IST__c -- the typo is in the API NAME, not just the label.
      Unfixable without a field rename plus every consumer updated
      (AdminDashboardController.cls:212, the IST flow, the page layout, the
      Training_Module_All_Access FLS block). Highest-risk naming trap here.

  T4  enableHistory is TRUE on the object but ALL 25 fields (and Name) carry
      trackHistory=false. History tracking is switched on with zero fields
      tracked -- you get an empty history related list, not an audit trail.

  T5  The Program_Version__c lookupFilter exists but is <active>false</active>.
      Anyone reading the metadata could reasonably assume version choices are
      constrained to the selected Program. They are not.

  T6  The IST-population flow's fOffsetMins CASE handles only ET/CT/MT/PT. A
      training on HT, UTC, AT or IST gets no matching branch. Since the GVS
      offers all eight and IST was added for the availability calendar, this is
      a live inconsistency worth checking before anyone books an IST cohort.

  T7  Niche__c is a restricted PICKLIST on this object AND a separate custom
      OBJECT queried by MockAvailabilityService.lookupNicheId(). The picklist
      labels must match the object's Name values or the lookup silently returns
      null. Prod was renamed "AIML Engineer" -> "AI ML Engineer" for exactly
      this reason.

  T8  There are ZERO validation rules on this object. Every invariant is Apex.
      Bypass the Apex (Data Loader, a flow, anonymous Apex) and nothing stops
      you double-booking a cohort or mismatching a Program Version.

  TESTING RULES THAT MATTER
  - Sandboxes do NOT run tests on deploy; PRODUCTION DOES. A class that has
    never been test-gated will be, the first time it reaches prod.
  - WITH SECURITY_ENFORCED in a class will FAIL in a production test run if the
    deploying user lacks FLS on the fields involved. This is exactly what broke
    the availability release -- see PART K, the two-phase production deploy.
  - Some behaviours are UNTESTABLE in Apex tests by construction: the
    AuraHandledException-from-REST failure is exempt in test context, and the
    cacheable-context DML limit is only enforced by the live Lightning runtime.
    Both had to be found with a real request and a debug log.
  - Preprod has pre-existing failures in modules this project does not own:
    AccountSchedulerJobTest, InterviewTriggerTest, InvoiceControllerTest,
    LockOverdueDeliverablesTest. Hence --test-level NoTestRun on preprod, and
    --test-level RunSpecifiedTests when you actually want your own tests
    validated.

  PERMISSION SET RULES, LEARNED THE HARD WAY
  P1  NO <license> element, ever. Once a perm set is created with a license
      Salesforce silently refuses to change it on redeploy, and a licensed perm
      set cannot be assigned to a Guest User. The only fix is: remove
      assignments, delete the perm set, redeploy clean.
  P2  Never add <fieldPermissions> for a REQUIRED field. Required fields get
      implicit access through objectPermissions; an explicit entry fails the
      deploy with "You cannot deploy to a required field".
  P3  XML ORDER MATTERS. ALL <fieldPermissions> blocks must come BEFORE ALL
      <objectPermissions> blocks, or you get a spurious "fieldPermissions
      duplicated" error.
  P4  A Guest User license does not allow allowEdit or allowDelete. Declaring
      them fails with "The user license doesn't allow the permission".
  P5  A perm set generated against one org's schema will fail against another's.
      Regenerate against the target, or strip the stray field references.
  P6  <description> is capped at 255 CHARACTERS and the deploy error is the
      unhelpful "data value too large". Note that XML entity escapes count
      against it -- an apostrophe becomes &#39; and eats 5 characters. Three
      deploys were burned on this while writing feature 29's perm sets.
  P7  Merge INTO an existing perm set rather than deleting and recreating when
      it already has assignments. A delete/recreate silently drops every
      assignment; adding grants to the existing record preserves them. This is
      how the feature 29 consolidation kept its 4 production assignments.

  LAYOUT AND FLEXIPAGE RULE -- DIFF BEFORE YOU OVERWRITE
  A Layout or FlexiPage deploy REPLACES the entire page. Any field the target
  org had but your source lacks silently DISAPPEARS from the page. This
  happened: deploying dev9's Recruiter Layout and Recruiter_Record_page to
  dev10 dropped Team_Lead__c, Manager__c and Designation__c off the recruiter
  page. The fields were not deleted -- a metadata deploy cannot delete fields
  and no destructiveChanges were sent -- but they vanished from the UI.
  preprod was unaffected because it does not have those fields at all, which
  incidentally proved dev10 and preprod have different Recruiter schemas.

  Do this instead: retrieve the target's copy, Compare-Object it against yours,
  and add only the new field to the target's existing page. Better still, keep
  org-specific layouts and record pages OUT of cross-org release manifests
  entirely.

PART I -- SECURITY MODEL
================================================================================

--------------------------------------------------------------------------------
I1. THE FIVE LAYERS
--------------------------------------------------------------------------------

  LAYER 1 -- NETWORK
    The LWR site is public. There is no Salesforce login page in front of it.
    Anyone can reach /login. Security starts at layer 2.

  LAYER 2 -- CREDENTIAL
    Username plus password against Candidate_Portal_Credential__c.
    Defences: one generic error for every failure mode, constant-time compare,
    five-strike lockout for fifteen minutes, an Is_Active kill switch.

  LAYER 3 -- SESSION TOKEN
    A random 32+ character Session_Id__c with a hard expiry, an active flag, a
    sliding heartbeat and a per-credential device cap.

  LAYER 4 -- APPLICATION-LAYER RECORD ACCESS  <-- THE LOAD-BEARING ONE
    CandidateContext resolves the token to exactly one candidate Id. Every SOQL
    filters by it. Writes additionally call an ownership assertion
    (assertOwned in the availability controller) before touching a record by Id.

  LAYER 5 -- PLATFORM OBJECT AND FIELD PERMISSIONS
    Candidate_Portal_Guest_Access grants the Guest User object read and FLS.
    NOTE what this layer does NOT do: it grants no record-level access at all.
    Guest Users have zero record visibility by default even with object read
    and FLS. That is why layer 4 is the one that matters.

--------------------------------------------------------------------------------
I2. WHY EVERY PORTAL CLASS IS `without sharing`
--------------------------------------------------------------------------------

It looks alarming in review and it is correct here.

Sharing rules govern which RECORDS a user can see. The Guest User can see none.
If the portal classes ran `with sharing`, every query would return zero rows and
the portal would be a blank page. `without sharing` puts Apex in system mode, and
the candidate-Id filter is what re-imposes isolation.

The trade this makes explicit: the isolation guarantee is only as good as the
discipline. There is no platform backstop. Which is why:

  - the pattern is stated as non-negotiable in CLAUDE.md,
  - every code review looks for the fromSession call and the candidateId filter,
  - and any method that takes a record Id from the client needs an explicit
    ownership check, not just a filter.

The IDOR guard pattern, from AvailabilityPortalController:

    private static void assertOwned(Id recordId, Id candidateId) {
        // fetch the record, compare its Candidate__c to candidateId,
        // throw if they differ.
    }
    // called at the top of updateMyAvailability and deleteMyAvailability

--------------------------------------------------------------------------------
I3. KNOWN SECURITY DEBT
--------------------------------------------------------------------------------

  D1  PASSWORDS ARE STORED IN PLAINTEXT.
      AuthService carries a header comment saying the plaintext compare is
      sandbox-only and must become SHA-256 before production data lands.
      Production has real candidates now. This is overdue.
      Migration requires three things, not one:
        (a) a hash function in AuthService,
        (b) a one-time backfill that hashes every existing row,
        (c) a forced password reset for anyone whose plaintext may have leaked.

  D2  recoverLogin EMAILS THE PLAINTEXT PASSWORD.
      Mitigated by sending it to the ACCOUNT OWNER (the recruiter/POC) rather
      than to whatever address the requester typed. Still, this must be
      rewritten as a one-time reset link the moment hashing lands.

  D3  recoverLogin REVEALS WHETHER AN EMAIL IS REGISTERED.
      An accepted product tradeoff, documented rather than accidental. Login
      itself does not leak this.

  D4  THE NEXT.JS CONSUMER SECRET WAS PASTED IN PLAINTEXT DURING SETUP.
      Rotate it before production use.

  D5  SERVER-SIDE CLASH CHECKS ARE SHARING-BLIND FOR THE GUEST USER.
      In the availability feature, availability-vs-availability overlap IS
      enforced server-side. Interview and session clash checks are enforced
      client-side for the portal; the server-side trigger checks cannot see the
      records under the Guest User's sharing. A determined caller could book
      over an interview.

  D6  APEX-LEVEL FLS BYPASS.
      System-mode Apex ignores FLS. Accepted because the API surface is small
      and every method is individually reviewed -- but it means adding a field
      to a DTO is a disclosure decision, not just a display decision.

--------------------------------------------------------------------------------
I4. SECURITY REVIEW CHECKLIST FOR ANY NEW PORTAL METHOD
--------------------------------------------------------------------------------

  [ ] First line is a CandidateContext call.
  [ ] The RIGHT variant: fromSessionReadOnly for cacheable=true or pre-callout,
      fromSession for writes, fromSessionRest for @RestResource.
  [ ] Every SOQL in the call tree filters by ctx.candidateId.
  [ ] Any record Id accepted from the client is ownership-checked, not just
      filtered.
  [ ] The return type is a DTO. No sObjects cross the Lightning boundary.
  [ ] No new field is exposed that the candidate should not see.
  [ ] The perm set grants only what is needed, and no allowEdit/allowDelete for
      the Guest.
  [ ] An error path exists that is VISIBLE in LWR (toasts do not render).

    was manually running sync code to compensate. Removing that condition made
    the flow fire on every save carrying a Pass or Fail. The manual step is gone.

K2. THE REPUBLISH RULE
--------------------------------------------------------------------------------

  Deploying an LWC updates the ORG. The live Experience site keeps serving its
  LAST PUBLISHED BUNDLE until you republish.

      sf community publish --name "Talent Hub" --target-org <alias>
      sf community publish --name "Candidate Space" --target-org dev9

  incognito window or after a hard refresh.

  republish -- or a republish of the wrong site. To prove it is not the deploy:

      sf project retrieve start --metadata "LightningComponentBundle:training" `
         --target-org preprod
      # inspect the retrieved bundle for your change
      # if it IS there, the org is fine -- republish the site

K5. THE PRODUCTION PATTERNS THAT WERE LEARNED THE HARD WAY
--------------------------------------------------------------------------------

  THE TWO-PHASE PRODUCTION DEPLOY
    Problem: production runs tests. AvailabilityController uses
    WITH SECURITY_ENFORCED. The new Availability fields had no FLS for the
    deploying user, so the test failed and the whole deploy rolled back -- but
    the FLS lived in a permission set that was IN the same deploy.

    Solution, in three steps:
      1. Deploy schema + record pages + the FLS-granting perm set, with NO Apex.
         No Apex means no test gate.
           sf project deploy start --manifest manifest/prod-phase1.xml ...
      2. Assign the perm set to the DEPLOYING USER:
           sf org assign permset --name Mock_Interview_Readiness `
              --target-org TechSaraProf
      3. Deploy Apex + LWC + Aura + Flow + QuickAction with RunSpecifiedTests.
           sf project deploy start --manifest manifest/prod-phase2.xml ...

    Sub-gotcha: Availability__c and Resume__c OVERRIDE their View action to a
    flexipage. Those pages must ship in the SAME phase as the object, or the
    deploy fails on a dangling reference.

  THE FLOW ACTIVATION TRAP
    In SANDBOXES, deploying a Flow whose metadata carries <status>Active</status>
    activates that version immediately -- even if you excluded the FlowDefinition.
    In PRODUCTION it did NOT: the new versions landed as DRAFT and the old
    versions stayed active.

    Fix for production: deploy a FlowDefinition with the ACTUAL production
    version numbers (they differ from the sandbox's), e.g.
    Interview_Create_Reschedule_Flow activeVersionNumber=5,
    Upload_Resume_Flow=3. Verify afterwards with a Tooling API Flow query.

  THE DRIFT PROBLEM
    dev10 and preprod run behind dev9, so a dev9-generated manifest references
    fields those orgs do not have. Things that had to be stripped for a
    cross-org release:
      Integration_Admin        excluded ENTIRELY (references hundreds of Data
                               Cloud / Einstein objects; already exists on the
                               targets; not feature-critical)
      Mock_Interview_Readiness Account.Time_Zone__c reference removed
      2 layouts                Final_Decision_By__c, On_break__c references
      2 flexipages             On_break__c, Pre_Enrolment_Requests__r,
                               Record.Time_Zone__c
    And the four field-dropping shared pages are permanently excluded from the
    production manifest (see PART H).

  CODE-ONLY DELTAS ARE SAFER
    The 2026-08-11 calendar promotion to three orgs shipped ONLY Apex and LWC --
    no schema, no pages, no perm sets, because those already existed on the
    targets and pages are drop-risky. That is the template for a low-risk
    promotion.

====================== project_nextjs_stem_portal_auth  (2026-08-04) ============

  A second candidate front end in Next.js logging in with the SAME credentials
  as the Experience Cloud portal. Next.js owns all UI and login; the LWR site
  does not render for those candidates. Salesforce is a headless REST backend.

  ARCHITECTURE ("Route A"): Next.js backend -> OAuth Client Credentials
  (integration user as Run As) -> thin Apex REST facade -> reuses AuthService
  and CandidateContext, so there is one lockout, one device cap and one token
  model across both portals. Chosen over the public-guest-Site approach because
  Next.js has a server tier that can hold the secret, and the org already uses
  this pattern for AWS.

    renamed and the old class deleted from dev9 and the repo.
    REST URL, kept generic and independent of the class name:
      /services/apexrest/v1/portal-auth/*
        POST /login  {username,password,clientIp} -> {ok, token, candidate}
        POST /logout {token}                      -> {ok}
        GET  /me     header Candidate-Session     -> {ok, candidate}

  reference_html_to_pdf_headless (2026-08-02)
    How to turn an HTML file into a PDF on this Windows box, which is how every
    handbook and credentials sheet in docs/ was produced.
    Two non-obvious requirements:
      1. --no-sandbox is REQUIRED. Without it Chrome/Edge exit with code 13 and
         write nothing.
      2. Write the PDF to the scratchpad FIRST, then Copy-Item to the
         destination. Writing directly to the project or Desktop path fails
         with exit 13.
    Working invocation:
      $chrome = "$env:ProgramFiles\Google\Chrome\Application\chrome.exe"
      $url = ([System.Uri]$htmlPath).AbsoluteUri
      $cliArgs = @("--headless=new","--no-sandbox","--disable-gpu",
        "--disable-dev-shm-usage","--no-first-run",
        "--user-data-dir=$scratchProfile",
        "--run-all-compositor-stages-before-draw","--virtual-time-budget=4000",
        "--print-to-pdf=$scratchOut",$url)
      Start-Process -FilePath $chrome -ArgumentList $cliArgs -Wait -PassThru `
        -WindowStyle Hidden
      Copy-Item $scratchOut $finalDest -Force
    Build the file:// URL with [System.Uri] -- an inline -replace '\\','/' trips
    a sandbox guard. Control margins with @page { size:A4; margin:12mm; } in the
    HTML CSS; new headless adds no browser header or footer. Use
    print-color-adjust:exact to keep dark banner backgrounds. There is no poppler
    on this box, so a generated PDF cannot be rendered back for visual checking.

L3. FEEDBACK MEMORIES -- HOW THE USER WANTS THE WORK DONE
--------------------------------------------------------------------------------

  These are working-style rules, not technical facts. They are as binding as the
  architecture.

  DEPLOY OUTPUT FORMAT (feedback_deploy_ui)
    Every sf deploy is a SINGLE PowerShell call with --json piped through
    ConvertFrom-Json so the only output is two lines: Status and Deploy Id. No
    100 KB progress-bar dump. Prefer --metadata "Type:Name" over long
    --source-dir lists.
    Every successful deploy is followed by a structured summary:
      one-line confirmation with the Deploy ID
      WHAT WAS WRONG      the old code or behaviour, in a fenced block
      NEW LOGIC           the new code or behaviour, in a fenced block
      RESULT              a small table or example with concrete inputs
      SIDE EFFECT         only if there is a non-obvious downstream effect
      WHY THIS ONLY AFFECTS X   only if the change is scoped
      VERIFY              2-4 bullets to check in incognito
    Skip sections that do not apply. The user reads the summary to decide whether
    to test or move on.

  NO WORKFLOWS FOR SCOPED DEPLOYS (feedback_no_workflow_for_deploys)
    For any sf deploy where the exact files can be named, run ONE PowerShell
    command. Do not wrap it in multi-agent orchestration. The user interrupted
    exactly this once and pointed at a previous deploy as the reference style.
    Workflows are for genuine fan-outs (research, design panels, parallel
    finders, adversarial verification), never for "I am about to run one CLI
    command."

  EXPLAIN, DO NOT POLL (feedback_prefer_explanation_over_choices)
    For open decisions, write out the issues and what each choice implies in
    prose, give a clear recommendation, and let the user reply in their own
    words. The user rejected a multiple-choice prompt and asked "what's going on
    / what will the issue be / what do I need to decide". They think in concrete
    problems, not abstract A/B options.

  CSS GOES PER-LWC (feedback_css_per_lwc)
    Component styles live in that component's own .css file. Touch
    dashboardStyles.css only for genuine cross-component tokens and utilities.
    The project moved to per-LWC CSS so teams can work on different tabs in
    parallel without colliding in a 2000-line shared file. Default to per-LWC.

  USERNAME FORMAT (feedback_portal_username_format)
    Candidate portal usernames MUST be firstname.lastname@talenthub.com -- all
    lowercase, dot separator, the fake talenthub.com domain, NEVER the
    candidate's real email. Also set Is_Active__c = true and
    Failed_Login_Count__c = 0 on creation. Password format in use:
    Firstname@ + 4 random digits (e.g. Usha@1332), stored plaintext per the
    current design. The candidate's real email stays on the Account for outbound
    mail and recovery.

  OVERFLOW CLIPS DROPDOWNS (feedback_lwc_overflow_clips_dropdowns)
    Never set overflow to anything but visible on a container holding form
    controls. Any non-visible overflow establishes a clipping context that hides
    absolutely-positioned descendants, including lightning-combobox and
    typeahead popovers. Symptom: the dropdown "opens" (aria state changes,
    clicks fire) but nothing appears. Use a SEPARATE wrapper for horizontal
    scrolling of tabular content, and prefer flex-wrap over overflow-x for
    filter rows.

  PER-ROW COLUMN SHAPES (feedback_lwc_per_row_column_conditional)
    Different column counts per group means TWO complete <table> elements gated
    by lwc:if -- not per-cell conditionals inside one shared table. The HTML
    parser normalises table structure and can strip <template> tags inside
    thead/tbody/tr. Same columns with different cell CONTENT per row is fine
    with per-cell conditionals. Add both isX and isNotX to the data, because LWC
    has no lwc:if={!x}. Accept the duplication for reliability.

  NEVER REGEX A SOURCE FILE (feedback_ps_regex_wrong_charset)
    Do NOT sanitise source files with PowerShell -replace and a wide unicode or
    hex character class. A conservative-looking range combined with a later
    broader pass ate EVERY lowercase 'i' from a 530-line LWC HTML file --
    <div> became <dv>, title became ttle, hundreds of attributes broke, and the
    deploy failed with "Invalid HTML syntax". The file had to be rewritten from
    scratch.
    Instead: target specific literal strings only. For encoding fixes, read with
    [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8) and write
    with System.Text.UTF8Encoding($false) -- and run NO additional regex passes.
    If characters do get mangled, rewriting the affected block from scratch is
    faster than un-mangling it. Always spot-Read after byte manipulation and
    before deploying.

  DIFF LAYOUTS BEFORE OVERWRITING (feedback_diff_layouts_before_overwrite)
    Deploying a shared Layout or FlexiPage wholesale across orgs silently drops
    fields from the page, because the deploy REPLACES the whole page. This
    dropped Team_Lead__c, Manager__c and Designation__c off dev10's recruiter
    page. The fields were not deleted -- a metadata deploy cannot delete fields
    and no destructiveChanges were sent -- but they vanished from the UI.
    preprod was unaffected because it lacks those fields entirely, which proved
    dev10 and preprod have different Recruiter schemas.
    Before deploying a shared page to another org: retrieve the target's copy and
    Compare-Object it. Ideally keep org-specific layouts and record pages out of
    cross-org manifests altogether and add just the new field to each target's
    existing page. dev10 was restored by re-adding the three fields to the layout
    and the "Recruiter Information" fieldSection of the flexipage (deploy
    0AfFZ0000029aJF0AY).

  GENERAL COMMUNICATION RULES (from CLAUDE.md, reinforced by every memory above)
    - Practical, deploy-as-we-go. Short responses preferred.
    - The user's messages often carry typos and shorthand. Interpret intent
      generously; do not pedantically question.
    - The IDE linter sometimes rewrites custom field API names (Candidate__c ->
      Account). That is the linter, not the user. Revert it.
    - Windows and PowerShell: $null not /dev/null, $env:VAR not $VAR, no &&.
    - For UI work: deploy, then ask the user to test in an INCOGNITO browser
      before claiming success.
    - After every code change, propose the exact sf command. Never claim "done"
      without a successful deploy ID.

PART N -- GOTCHAS AND TROUBLESHOOTING
================================================================================

Numbered so they can be cited. Each one has actually happened.

--- PLATFORM AND SITE ---

  N-01  PORTAL SHOWS AN EMPTY STATE (no deliverables, no sessions)
        Cause: the Guest User does not have Candidate_Portal_Guest_Access -- or
        it is on the WRONG guest user. Verified in production once: the perm set
        was on "Talent Hub Site Guest User" while the portal ran as "Techsara
        Candidate Hub Site Guest User".
        Fix: Setup -> Digital Experiences -> your site -> Administration ->
        Guest User -> check the assigned permission sets.

  N-02  A DEPLOYED LWC CHANGE DOES NOT APPEAR
        Cause: the site was not republished, or the WRONG site was republished.
        Fix: sf community publish --name "<the right site>" --target-org <alias>.
        dev9 = "Candidate Space". dev10/preprod/prod = "Talent Hub".
        Prove the org is fine first by retrieving the bundle and inspecting it.

  N-03  EVERY PAGE RETURNS "INVALID PAGE"
        Cause: the Guest Profile is not in the Network's networkMemberGroups.
        Fix: add it via Network metadata or Workspaces -> Administration ->
        Members. Note the Guest User profile does not appear in the standard
        Members list UI.

  N-04  /s/ PREFIX CONFUSION
        LWR sites have NO /s/ prefix. URLs are /<siteslug>/login and /<siteslug>/.
        Redirect logic must compute the prefix from window.location.pathname.

--- PERMISSION SETS ---

  N-05  "You cannot deploy to a required field"
        Cause: an explicit <fieldPermissions> entry for a required field.
        Fix: remove it. Required fields get access via objectPermissions.

  N-06  "fieldPermissions duplicated"
        Cause: XML ordering. ALL fieldPermissions blocks must precede ALL
        objectPermissions blocks.

  N-07  A PERM SET SILENTLY REFUSES TO CHANGE ITS LICENSE
        Cause: once created with a <license>, Salesforce keeps the original
        forever on redeploy -- and a licensed perm set cannot go to a Guest User.
        Fix: remove assignments, delete the perm set, redeploy license-free.

  N-08  "The user license doesn't allow the permission"
        Cause: allowEdit or allowDelete declared for the Guest User.
        Fix: grant Read + Create only. Writes still work through system-mode
        Apex; guard them with an ownership assertion.

  N-09  A PERM SET REFERENCES A FIELD THAT DOES NOT EXIST IN THE TARGET
        Cause: it was generated against a different org's schema.
        Fix: regenerate against the target, or strip the stray references. This
        is routine when promoting from dev9 to the orgs behind it.

--- APEX AND RUNTIME ---

  N-10  "Too many DML statements: 1" ON A CACHEABLE METHOD
        Cause: @AuraEnabled(cacheable=true) plus CandidateContext.fromSession,
        whose heartbeat is a DML.
        Fix: cacheable reads use fromSessionReadOnly. Writes keep fromSession.
        This does NOT reproduce locally, as an admin, or under System.runAs --
        only the live Lightning cacheable runtime enforces it. Diagnose with a
        TraceFlag on the site Guest User and read the ApexLog.

  N-11  A PORTAL GRID IS EMPTY BUT THE RECORDS EXIST
        Cause: the method returned raw sObjects and the Guest's missing FLS
        stripped the fields, so the LWC filtered every row out.
        Fix: return a DTO. Never sObjects across the Lightning boundary.

  N-12  A PORTAL LWC IS TOTALLY BLANK BUT IMPERATIVE WRITES WORK
        Cause: the session token was read in connectedCallback, but @wires keyed
        on $sessionId provision BEFORE connectedCallback runs, so they fired once
        with undefined and never re-ran.
        Fix: sessionId = getSession(); as a CLASS FIELD INITIALIZER.

  N-13  "Can only throw this exception type from VisualForce or Aura context"
        Cause: AuraHandledException thrown from a @RestResource.
        Fix: use the catchable internal variants -- AuthService.loginInternal and
        CandidateContext.fromSessionRest. Unit tests are exempt from this rule,
        so only a live REST call reproduces it.

--- LAYOUTS AND PAGES ---

  N-27  FIELDS DISAPPEAR FROM A RECORD PAGE AFTER A DEPLOY
        Cause: a Layout or FlexiPage deploy REPLACES the whole page, so anything
        the target had and your source lacked is gone. The fields still exist;
        they are just off the page.

--- TOOLING AND ENCODING ---

  N-29  A SOURCE FILE IS SILENTLY CORRUPTED AFTER A POWERSHELL PASS
        Cause: -replace with a wide unicode or hex character class. This once ate
        every lowercase 'i' from a 530-line LWC HTML file.
        Fix: never do it. Target literal strings only. If it happens, rewriting
        the affected block from scratch is faster than un-mangling it.

  N-30  APEX SOURCE SHOWS DOUBLE-ENCODED CHARACTERS
        A UTF-8 file re-read as Windows-1252 and re-saved turns a middle dot into

  N-31  THE IDE LINTER REWRITES A CUSTOM FIELD API NAME

  N-32  rollbackOnError HIDES A PARTIAL SUCCESS

        deploy rolled back. Always verify org state with SOQL afterwards.

  N-33  RETRIEVE WRITES TO A TEMP PATH

        directories with retrieved metadata are unreliable.

  N-34  HEADLESS CHROME EXITS WITH CODE 13 AND WRITES NO PDF

  N-46  "You do not have access to the Apex class named 'X'"
        Cause: the permission set granting that class is not assigned to the
        logged-in user.
        THE DIAGNOSTIC VALUE OF THIS ERROR: users holding "Author Apex" -- every
        System Administrator -- BYPASS Apex class security entirely. So an admin
        literally cannot produce this error. Seeing it proves you are logged in
        as a community/portal user, which is the correct way to test. Testing a

  N-47  A TRAINER-SCOPED FILTER RETURNS ALMOST NOTHING

  N-48  STAT TILES DO NOT ADD UP TO THE TOTAL

        Fix: when consolidating, ADD grants to the existing perm set instead.
        Renaming the API name has the same effect as delete/recreate, which is

  N-51  A TOOLING-API CustomTab QUERY REPORTS A TAB AS MISSING WHEN IT EXISTS

        Seen once against production: Status and Deploy Id both blank, and the
        deploy had not fully submitted. Confirm with a Tooling query on
        DeployRequest (ORDER BY CreatedDate DESC) or simply re-run. Never assume
        a blank result means success -- verify the org state.

  N-53  A COMPONENT THAT WORKS INTERNALLY SHOWS NOTHING ON AN EXPERIENCE SITE

PART P -- GLOSSARY
================================================================================

  CANDIDATE            A trainee. A Person Account in Salesforce. Never a User.
  COHORT / SLOT        Cohort__c. A batch of candidates. The UI calls it a
                       "Slot" and its records are named "Slot 133" etc.
  DELIVERABLE          An assignment a candidate must submit. Deliverable__c.
  DELIVERABLE RESULT   One submission attempt on a deliverable, with its grade.
  GUEST USER           The unlicensed Experience Cloud identity that every
                       portal visitor runs as, including logged-in candidates.
  IRT                  Resume-based / individual training, as opposed to a
                       cohorted group program. IRT trainings often lack a
                       Start_Date and a Cohort, which is why several fallbacks
                       exist.
  LWR                  Lightning Web Runtime -- the modern Experience Cloud
                       template. No /s/ prefix, no ShowToastEvent.
  MOCK                 A practice interview during training. Stored as an
                       Internal_Interview__c with Candidate_Training__c set.
  NICHE                A technical track (AI/ML, Full Stack, ...). A Picklist on
                       Candidate_Training and a Lookup on Internal_Interview --
                       see N-16.
  PROGRAM              The catalog item. Program__c.
  PROGRAM VERSION      The versioned configuration of a program. Program_Version__c.
                       Every behavioural switch lives here.
  RECRUITER            Recruiter__c -- the employee/trainer object. Bridged to a
                       Salesforce User by Recruiter_User__c.
  SESSION              A scheduled meeting. Session__c. Serves training sessions,
                       mocks, interviews, onboarding and background checks.
  SESSION ATTENDEE     Session_Attendee__c. A candidate on a group session who is
                       not the master.
  SESSION WINDOW       Session_Window__c. A reusable daily time window for a
                       cohort, e.g. "Mon-Fri 7-9 PM ET".
  STEP                 CandidateTrainingStep__c -- the per-candidate instance.
  STEP TEMPLATE        StepTemplate__c -- the reusable definition on a
                       Program_Version.
  TRAINING             Candidate_Training__c. One candidate's enrolment in one
                       Program_Version.
  TWIN                 An internal controller and its session-authenticated
                       portal counterpart, sharing public helpers.
