       1. Introduction & Scope
       The Training Module is the core delivery engine of the Techsara Candidate Portal. It handles the end-to-end
       journey of a candidate through structured technical training: enrolment into a Program, day-by-day module
       scheduling in a Cohort (called a "Slot" in operational language), delivery of live Sessions, submission and
       evaluation of Deliverables, and periodic Mock Interviews as competency checks.
       Everything the candidate sees on the portal — the Overview tiles, Training tab, Deliverables tab, Mock Interview
       tab, session calendar — is served by Apex controllers running as the unlicensed Guest User, using a custom
       session-token model rather than per-candidate Salesforce licences. All authoritative gating happens at the Apex
       layer via the CandidateContext pattern.


          Coverage. This handbook covers: the Candidate Portal training surfaces, the Admin Training Dashboard (list + chart
          views), the Session/Session Window scheduling stack, the Deliverable submission and roll-up pipeline, the Mock
          Interview subsystem (v1–v6.9+), the Recruiter Break Scheduler, and every automation flow and permission set that
          governs the above. Non-training features (Marketing, Recruiting, B2B Interviews, Onboarding) are out of scope except
          where they intersect (e.g. Session.Purpose values).




          1.1 How to read this document
           Objects are described with every custom field, its type, and a one-line purpose. Standard system fields (Owner,
           CreatedDate, etc.) are omitted.
           Picklist statuses are shown as coloured pills for quick lifecycle recognition:       Planned        Active   Paused

             Completed     Dropped

           Flow names and API names appear in mono . UI labels appear in regular text.
           Use cases at the end tie the pieces together into end-to-end playbooks.

       2. Vocabulary — Slots, Cohorts, Windows &
       Sessions
       Terminology matters here because the operational language and metadata names diverge. This table is the source
       of truth for the rest of the document.

        Operational         Metadata name                          Meaning
        term

        Slot                Cohort__c                              A group of candidates progressing through a program together, with
                                                                   a defined start and end date.

        Session Window      Session_Window__c                      A recurring daily time slot inside a Slot — e.g., "Morning Batch 9–11
        / Window                                                   AM IST". A Slot can host multiple Windows for different candidate
                                                                   groups.

        Session             Session__c                             One actual scheduled meeting (a training day, an interview, a
                                                                   welcome call, etc.). One per calendar day per Window, per candidate.

        Session Attendee    Session_Attendee__c                    An additional candidate riding on someone else's master Session —
                                                                   used for Group Sessions.

        Program             Program__c                             A named curriculum (e.g., "Advanced AI/ML Training").

        Program Version     Program_Version__c                     A specific configured version of a Program — controls session type,
                                                                   duration, mock cadence. Versions are frozen once Published.

        Candidate           Candidate_Training__c                  One candidate's enrolment into one Program Version — the live
        Training                                                   tracker.

        Training Step /     CandidateTrainingStep__c               One day/module of a Candidate Training — think "Day 3 — LSTM
        Module                                                     basics".

        Step Template       StepTemplate__c                        The reusable blueprint of a module, cloned into Training Steps when a
                                                                   Candidate Training is created.

        Deliverable         Deliverable__c                         A task or artefact the candidate must submit tied to a Step (e.g., a
                                                                   quiz, an assignment).

        Deliverable         Deliverable_Result__c                  One submission attempt against a Deliverable — carries the AWS AI
        Result                                                     score.

        Mock Interview      Internal_Interview__c                  A periodic competency check. Same object as external interviews; a
                                                                   Mock is identified by Candidate_Training__c being populated.

        Interview Type      Interview_Type__c                      Lookup record naming the mock (e.g., "AI ML - V1 - Week 3", "AI ML -
                                                                   V1 - Final Mock").



          The mental model. Program → Program Version → Cohort (Slot) with N Session Windows → each Window has M
          Candidate Trainings enrolled → each Training has D Training Steps → each Step has one Session (per day) and 0..K
          Deliverables. Mock Interviews sit alongside Sessions but attach at the Training level, not the Step level.

       4. Lifecycles & State Machines

          4.1 Candidate Training
            Planned            →         Active         →         (Paused)       →        Completed               OR         Dropped

        1. Planned — created via Candidate_Training_Creation screen flow. Portal shows a "Training is being set up"
           banner.
        2. Active — admin flips when training goes live. Sessions/deliverables begin surfacing to the candidate.
        3. Paused — temporary halt (medical leave, batch merge, etc.). Portal banner explains.
        4. Completed — end-of-program. Deliverables and steps typically already terminal.
        5. Dropped — cascade fires. Set Drop_Date__c first (or let Candidate_Training_Auto_Set_Drop_Date stamp
           today's date). Then Candidate_Training_Dropped_Cascade runs and:
               Calls CandidateTrainingDropHandler to handle Sessions (solo cancel, attendee delete, or master
               promotion).
               Sets Deliverables →        Dropped   for records with due-date ≥ Drop_Date and status not in
               (Approved/Failed/Dropped).
               Sets Steps →        Dropped   for records started on/after Drop_Date and not Completed.

           Records dated before Drop_Date keep their prior status.



          4.2 Deliverable
                                                                                          Approved /                         Locked /
           Not Active          →         Active         →          Pending       →                                OR
                                                                                            Failed                           Dropped

        1. Created      Not Active    when the parent Step is generated.

        3. Candidate uploads via portal S3 flow → Deliverable_Result__c row inserted with Result_Status                       Pending   .

          Unscheduled          →       Scheduled        →         Completed          OR      Rescheduled / Cancelled

        1. Created      Unscheduled    — no meeting link yet.
        2. Session_Scheduling_Callout_Flow fires (condition: Status=Unscheduled AND Meeting_Link=null AND
           External_Meeting_ID=null), builds Zoom payload from Host_User + Candidate_Email +

           Additional_Attendee_1/2, calls the external service, writes back Meeting_Link/External_Meeting_ID/Passcode.
           Status flips to   Scheduled   .
        3. Session_To_Calendar_Event syncs the Session to a calendar Event on the host's calendar.
        4. After delivery, host records feedback ( Host_Feedback__c is REQUIRED to save Status = Completed —
           validation rule Require_Host_Feedback_On_Complete ). Status →            Completed   .
        5. On Completion, SessionCompletionAttendeeTrigger propagates to attendees' Step statuses, and
           Session_Complete_Activate_Deliverables activates downstream deliverables.
        6. Reschedule: Status → Rescheduled. Validation rule Lock_Rescheduled_Session then blocks any further edit to
           the record — a new Session record must be created for the new slot.
        7. Cancel: Status →      Cancelled   . Reached via drop cascade (solo) or manual admin action.



          4.4 Session Window
           Upcoming          →           Active        →      Completed

           Created    Upcoming     via sessionWindowCreator LWC or Program_Creation flow. Start_Date auto-populates
           from Cohort. Activate_From = Start-7 days.
            Session_Window_Status_Roll (scheduled) flips Upcoming →              Active   when Cohort.Start_Date is reached, then
           Active →    Completed    when Cohort.End_Date passes.
            Session_Window_Enforce_Unique_Cohort blocks creating a second Window on the same Cohort + PV combo.
           Portal booking increments Booked_Count__c and caps at 5. Admin can bypass the cap via
            assignSessionWindowToTraining quick action.



          4.5 Mock Interview
        1. Expectation computed by MockScheduleCalculator from PV config (Weekly / Once / End of Program /
           Custom).
        2. Booking window opens Mock_Booking_Window_Days__c before the mock date (default 4 working days).
        3. Candidate picks a slot from MockAvailabilityService.listMockSlots — free interviewer × candidate TZ ×
           granularity.
        4. Book via bookMockSlot : inserts Internal_Interview (Status=Unscheduled) → Mock_Auto_Create_Session flow
           inserts the linked Session → callout flow generates Zoom link → calendar sync.
        5. Reschedule allowed up to Mock_Reschedule_Lock_Days__c working days before the mock. After that, the
           "Reschedule" button locks and the candidate must contact CS.
        6. Result deadline = mock date + Mock_Result_Deadline_Days__c working days (default 3).
        7. Missed result: MockDeadlineEnforcer (scheduled) sends reminder emails — interviewer at +4h,
           interviewer+trainer at +7h, cap 2 emails. After that, applies Mock_Miss_Action (default: Drop Training →
           triggers full drop cascade).
        8. Failed result: Mock_Result_Handler flow applies same miss action.

       11. Common Use Cases & Playbooks

          UC-1: Enrol a new candidate into a training
        1. Admin runs Candidate_Training_Creation screen flow.
        2. Picks Candidate, Program, Program Version (only Published PVs shown).
        3. Picks Cohort (Slot) → Session Window auto-populates.
        4. Sets Time Zone, Start Date.
        5. Assigns Trainer.
        6. Flow inserts Candidate_Training__c with Status =             Planned   .
        7. Deliverables are pre-created in     Not Active   state.
        8. Steps are cloned from the PV's Step Templates.
        9. Sessions (if Auto_Create_Sessions on Program) are inserted             Unscheduled   .



          UC-2: Candidate books into a Session Window
        1. Candidate opens portal Training tab.
        2. Sees "Book your Session Window" card (only if Activate_From ≤ today).
        3. trainingSlotPicker LWC calls getBookableSessionWindows → filters by PV match, Booked_Count < 5, Status
           Upcoming/Active.
        4. Candidate picks a Window → calls bookSessionWindow .
        5. If Window has no live sessions yet → creates fresh Sessions under this candidate (they become the master).
        6. If Window has live sessions → creates Session_Attendee rows for this candidate under the existing masters.


          Bug fixed August 2026. The "Window has live sessions" check now excludes Status = Cancelled . Previously, if the
          original master dropped and their Sessions were cancelled, new candidates would be stapled as attendees onto dead
          Sessions with no Zoom link.




          UC-3: Trainer marks a Session Complete
        1. Trainer edits the Session record; fills Host_Feedback__c ; sets Status = Completed.
        2. Validation rule Require_Host_Feedback_On_Complete passes.
        3. Session_Complete_Activate_Deliverables flow fires: activates every Deliverable under the corresponding
           Step and emails candidate with HTML digest + portal link.
        4. SessionCompletionAttendeeTrigger propagates completion to all attendees' Steps.



          UC-4: Candidate submits a deliverable
        1. Candidate opens portal Deliverables tab; sees Active deliverables.
        2. Uploads file → LWC calls createPendingResult → getUploadUrl (pre-signed S3 URL) → PUT to S3 →
            finalizeSubmission .
        3. Deliverable_Result inserted with Result_Status =          Pending   ; Deliverable.Status = Submitted.
        4. AWS AI pipeline processes the file; calls back DeliverableResultRest with score + feedback.
        5. Result_Status flips to Pass/Fail.

===== PAGE 29 / 32 =====
        6. Deliverable_result_roll_up_status rolls to parent — Pass ⇒               Approved   , Fail ⇒   Failed   .



          UC-5: Candidate books a Mock Interview
        1. Candidate opens Mock Interview tab.
        2. getMockBookingState returns state — book-now, booked, awaiting-result, etc.
        3. Candidate picks a slot from listMockSlots .
        4. bookMockSlot guardrails run (see 8.3), interviewer picked, Internal_Interview inserted (Scheduled).
        5. Mock_Auto_Create_Session creates linked Session → callout → calendar → email invites.



          UC-6: Drop a candidate mid-training
        1. Admin sets Drop_Date__c (or leaves blank → today).
        2. Flips Status to    Dropped   .
        3. Candidate_Training_Dropped_Cascade fires:

               Deliverables due on/after Drop_Date → Dropped.
               Steps started on/after Drop_Date → Dropped.
                   CandidateTrainingDropHandler handles Sessions: solo cancel · attendee delete · master promotion to
               earliest remaining Session_Attendee for group sessions.

        4. Records before Drop_Date keep their prior status (audit-preserved).



          UC-7: Recurring break in a trainer's calendar
        1. Trainer opens their Recruiter record → clicks Manage Recurring Break button.
        2. Recruiter_Break_Manager flow presents mode picker (Schedule / Delete).
        3. On Schedule: pick Subject, Duration (1 week / 2 weeks / 1 month), Start Date, Start/End Time, Time Zone.
        4. Flow creates a Recurring_Break_Series, loops each weekday in range, skips weekends, skips days where an
           existing event overlaps the break time (time-overlap check as of Aug 2026), creates one Event per remaining
           day linked to the Series.
        5. On Delete: pick a Series → all its Events + the Series record are removed.



          UC-8: Add an ad-hoc extra session to a Session Window
       Say a Cohort ran through Aug 6 and you need a make-up on Aug 7 with the same attendee group but no Step
       exists for it. Use anonymous Apex:
        1. Load the Session_Window.
        2. Query the most recent non-cancelled Session in the window as a "template" (source of master + times +
           trainer).
        3. Insert a new Session with Status=Unscheduled, Candidate_Training_Step=(template's step to satisfy required
           field), Scheduled_Date=Aug 7.
        4. Copy Session_Attendee rows from the template session onto the new one — each attendee keeps their own
           Candidate_Training + Candidate_Training_Step.
        5. Callout flow auto-fires → Zoom link generated → invites sent.

===== PAGE 30 / 32 =====
          UC-9: Reassign master when the original candidate is moved between
          windows
       Session records' Candidate_Training__c points to the master's training — even if that candidate has been
       moved to a different Session Window. To rebase:

        1. Detach cancelled Sessions from the Window: Session_Window__c = null on those rows so future assignment
           code takes the "create fresh" branch.
        2. Re-run AdminSessionAssignmentController.assignTrainingToWindow for the new master candidate — fresh
           Sessions get created under them, new Zoom links minted.
