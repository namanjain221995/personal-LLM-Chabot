# observability

Operational data about how the system ran, kept apart from the data the system
answers questions about.

    salesforce_knowledge/runtime_schema   what the org's schema is
    salesforce_knowledge/record_data      what the org's records are
    observability/tracing                 what one request did

    tracing/
      db/         traces.sqlite   canonical, append-only, WAL
      exports/    query_traces.csv · query_trace_events.csv · traces.duckdb
      logs/
      snapshots/

## Why SQLite is canonical and DuckDB is an export

The store has two writers by design: the knowledge service owns steps 1-3 and
the orchestrator owns steps 4-6, both appending to one file so a question reads
as one row instead of two halves nothing joins. It also has readers that must
not wait: the `/traces` endpoints and, later, an evaluation run.

DuckDB cannot do that. Measured, two processes, one file:

    process 1 holds a write connection
    process 2 WRITE: IO Error: Could not set lock on file ...
                     Conflicting lock is held in /usr/bin/python3.12 (PID ...)
    process 2 READ : (same lock error)

The lock is exclusive and it excludes readers too. SQLite in WAL mode takes
concurrent readers and a serialised writer, which is exactly this workload --
one row per question, not a write path under load.

So DuckDB is produced FROM the canonical store rather than replacing it. It is
regenerated by the exporter, never written to directly, and therefore cannot
drift from what actually happened. Analytical SQL and joins over traces work;
the write path keeps the concurrency it needs.

## Exporting

    python scripts/export_traces.py                  # CSV + DuckDB
    python scripts/export_traces.py --format csv

## Inspecting one request

    python scripts/inspect_trace.py --latest 10
    python scripts/inspect_trace.py --trace-id kt_<hex>
