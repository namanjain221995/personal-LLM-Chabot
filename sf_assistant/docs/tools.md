# Tools

Generated by `scripts/gen_tools_doc.py` from `src/sf_assistant/tools/registry.py`. Do not edit this file by hand: change the registry, then run `.venv/bin/python scripts/gen_tools_doc.py`. `tests/test_tool_registry.py` fails when this file is not current.

Every tool a model can call is defined once, in `sf_assistant.tools.registry`: its name, its description, its input schema (JSON Schema, the MCP `inputSchema`) and the method that runs it. The registries build their tools from these definitions:

| Tool set | Registry | Tools | Who gets it |
|---|---|---|---|
| Knowledge, one object | `sf_assistant.tools.knowledge_tools.ToolRegistry` | 15 | the knowledge agent with exactly one knowledge file (`--knowledge FILE`) |
| Knowledge, several objects | `sf_assistant.tools.knowledge_tools.MultiToolRegistry` | 18 (+3 component tools) | the knowledge agent with several files (default: every file in `knowledge/objects/`); the MCP server |
| Flow components | `sf_assistant.tools.component_tools.ComponentTools` | 3 | appended to the several-object tools when `knowledge/components/` holds an `index.json` (the full knowledge agent, the MCP server); not the one-object registry, not the lean step |
| Records | `sf_assistant.tools.record_tools.RecordTools` | 14 | the record agent (local warehouse snapshot) |

The lean knowledge step (`sf_assistant.agent.lean`) offers a subset of the knowledge tools with the same definitions.

Each registry gives its tools as `list_tools()` (MCP `tools/list`: `name`, `description`, `inputSchema`) and `openai_tools()` (`{"type": "function", "function": {name, description, parameters}}`), in the order below, and runs one with `call(name, arguments)`, which never raises.

Placeholders on this page: `{object}` is the API name of the object of the knowledge file, `{sections}` the section ids of that file (one enum value each), `{objects}` the API names of the loaded objects (sorted, one enum value each) and `{first object}` the object of the first loaded knowledge file.

## Flow component tools

`ComponentTools` over the flow components (`knowledge/components/`: `flows/<ApiName>.json` and `index.json`, loaded by `sf_assistant.knowledge.components`): 3 tools, offered after the several-object tools when the components are loaded (`config.COMPONENTS_DIR`, `SFA_COMPONENTS_DIR`). They take no object enum: code resolves every name (API name, label, title or alias, with did-you-means; `find_usages` also takes an object label). Budgets (`config.LIMITS`): `search_components` at most 4,000 characters (one card per flow, about 5 fit; `k` 5 by default, at most 10; `more` counts only the hits that score close to the best one); `get_component` summary at most 3,500 (shortened least needed first: dev10 notes, meaning, caveats, lists, and the effect lines last), its `effects` (one line per effect), `logic`, `fields` and `caveats` levels in pages of at most 6,000 (`page`, `pages`, `next_page`; an item larger than a page is split into `part`s); `find_usages` at most 40 rows and 9,000 characters, then `more`, always with `not_covered`. A writer row gives `values` (literal) and `value_from` (a variable, a field or a formula); with `value`, the rows write that literal value, `values_not_fixed` may write it, `values_unknown` (Apex, not built) are not scanned and `writes_other_values` write other literal values only. The files' development evidence is stripped when they are loaded: no result carries it, and the card index never holds it.
